# 案例研究:低配 VPS 上的 Resilio Sync 减负与守护

> 本文整理自真实生产环境的开发与运维日志。服务器标识已脱敏:公网生产机记作 **prod**,内网测试机记作 **lab**。

## TL;DR

一台入门级 VPS 上跑着约 99 个 Resilio Sync 同步文件夹,官方 Web UI 的重轮询把它压得喘不过气。本项目分三层解决:**本地面板**(远端只收最小 JSON,设计目标削减 80-90% 请求量)、**sync-guard 守护**(OOM 配置保护 + 假死健康检查 + 稀缺性优先分批调度,systemd 常驻)、**严格的安全模型**(本地绑定 + SSH 隧道 + Bearer Token + 日志脱敏)。上线后经历并修复了两次代表性生产事故,复盘见 §3、§4。

## 1. 问题

- 远端是入门级 VPS,常驻 ~99 个同步文件夹并发;
- 官方 Web UI 每次加载 2-5MB 静态资源,前端每 3 秒轮询 5 个以上接口,机器资源大量耗在"伺候管理界面"上;
- 真实需求:管理功能一个不能少(暂停/恢复/限速/加删文件夹/批量操作),但远端负载必须大幅下降。

## 2. 方案:三层设计

### 2.1 本地面板:把负载从远端搬走

核心思路:**远端只出数据,本地负责渲染**。

- 只对远端发 JSON API:仪表盘每轮仅一次 `getsyncfolders(discovery=1)`,全局速度由返回字段求和(比原计划的多次调用更省);
- 轮询间隔从官方 3 秒放宽到 5-10 秒;写操作(限速/暂停/恢复)只在用户手动触发时发生;
- 兼容老版本 Resilio 的弱加密 TLS(自定义 TlsAdapter);
- 设计目标:远端 API 请求量削减 80-90%。

### 2.2 sync-guard:服务器端 systemd 常驻守护

1. **OOM 配置保护**:rslsync 被 OOM SIGKILL 后,文件夹暂停状态与限速配置会因未落盘而回退。guard 周期备份配置,检测到重启后用最近备份恢复;
2. **假死健康检查**:进程活着 ≠ 服务活着(见 §3),周期探测,异常时自动重启;
3. **稀缺性优先分批调度**:带宽有限时,按 D(有下载需求)> C(有上传需求)> B(做种充足)> A(无需求)分级,分批暂停/恢复,把带宽集中给最需要的文件夹。

### 2.3 安全模型

- 面板仅绑定 `127.0.0.1`,经 SSH 隧道访问,不公网暴露;
- guard HTTP 管理接口使用 Bearer Token,凭证仅经环境变量注入,不落盘;
- 服务器端状态/日志脱敏:只含计数与时间戳,不含文件夹标识,防第三方查看泄露;
- 未登录 API 一律 401;写操作做 Origin 同源校验。

## 3. 事故一:活着,但已经死了(HTTP 线程池饿死)

**现象**:rslsync 进程活着(S 状态、CPU 8%、内存 465MB),但 guard 每 15 秒刷一次 ReadTimeout,status 已 5.5 小时未更新,备份与调度全部停摆。

**定位**:

- 断裂点:调度周期 #432 耗时 10025ms,正好撞上 10 秒读超时的临界值,此后连续超时;
- 诱因:rslsync 触发大量 `ConnectMorePeers` + 隧道 `SE_NET_TIMEOUT`(对端节点连接全部超时),**HTTP 线程池被挂起连接耗尽**;此前两天已有 1494 + 851 条间歇超时的持续劣化——事故不是突发的,是劣化到了临界点。

**为什么守护没拦住**:现有假死检测只探测"登录是否成功"(token.html)。本次故障中登录正常(0.15s 返回 200),卡死发生在 **action 层**——登录探针恒返回健康,fail_streak 永不累加,检测从不触发;线程数阈值(8)也未达到。**检测打错了层。**

**修复**:健康检查改为"登录 + 真实 action 双验证"——新增 `_probe_healthy()`:先登录,再实际调用一次轻量 action(`getsessionstats`,超时 8s),两者都成功才算健康。

**验证**:mock 5 种故障场景(登录 500 / token 解析失败 / action 400 / action 超时 / 全部正常)全部通过;真机实测健康状态下 `getsessionstats` 6 次全 200(0.01-0.04s),确认不误判;部署后 45 秒内零误触发,备份调度恢复。

**教训**:健康探测必须打在真实会故障的那一层。"能登录"和"能干活"是两回事。

## 4. 事故二:pgrep 取错进程,OOM 闸门形同虚设

**现象**:面板内存卡片显示 ~2.2MB,与实际(600-750MB)差了三百倍。

**根因**:服务器上并存两个同名 rslsync 进程——一个残留测试实例(PID 1015006,已存活 3.6 天,RSS 仅 ~1.5MB)和 systemd 主进程(PID 1185275,RSS 600-750MB)。而 `guard_webapi.read_mem()` 与 `sync_guard._mem_gate_blocked()` 都用 `pgrep -x rslsync` 取 **PID 升序第一个**——永远命中那个 1.5MB 的残留进程。

**连带伤害**:70% 阈值的内存闸门(OOM 防线)因此永远读到 1.5MB,从未真正工作;且残留进程位于 user.slice、无 memory.max 限制,即便读到正确值,按 cgroup 判断也会直接放行。这与近期 `last_restart_reason=oom` 的记录相互印证——防线失守不是理论风险,是已经发生过的事实。

**修复**:两处统一改用 `_rslsync_pid()` helper——优先向 systemd 要主进程(`systemctl show -p MainPID resilio-sync`),兜底在 pgrep 结果中选 VmRSS 最大者。

**验证**:`read_mem()` 返回正确 pid 与 RSS(≈700MB),cgroup 数据齐全;带 Bearer Token 的 `/api/status` 确认 ok;残留进程清除后仅剩主进程。

**教训**:

1. 同名多进程是运维常态,指标采集必须锚定"正确的那个进程";
2. systemd 管理的服务,优先向 systemd 要 PID,而不是在进程表里猜;
3. 防护机制要定期"真开一枪"验证——它失效的时候不会通知你。

## 5. 小事故:为什么"时不时退出登录"

Flask 的 session 默认是**会话级 cookie**(无 Expires/Max-Age),浏览器一关就删——服务器地址、凭据、guard 配置全部跟着丢。修复:`PERMANENT_SESSION_LIFETIME = 30 天` + 登录时 `session.permanent = True`。

顺带修正了一个文档里的错误表述:此前把 Flask session 称为"客户端加密",实际上它是 **HMAC 签名 cookie**——base64 可解码(防篡改,不防偷看)。安全机制的描述必须精确,差一个词就是错误的安全认知。

## 6. 复盘

这个项目最终交付的不是一个面板,而是一套针对低配服务器的完整运维方法:

| 层 | 问题 | 手段 |
|---|---|---|
| 请求量 | 官方 WebUI 重轮询压垮低配机 | 本地渲染 + 最小 JSON + 单调用合并 |
| 进程存活 | 假死(活着但不可用) | action 层双验证健康检查 |
| 内存/OOM | OOM 后配置回退 | 配置周期备份 + 重启恢复 + 内存闸门 |
| 带宽 | ~99 文件夹争抢有限带宽 | 稀缺性优先(D/C/B/A)分批调度 |
| 凭据 | 凭证管理 | 环境变量注入 + Bearer Token + 隧道访问 |

给遇到类似场景的人一份 checklist:

- [ ] 你的健康检查探的是"能登录"还是"能干活"?
- [ ] 你的指标采集在多进程环境下锚定的是哪个进程?
- [ ] 你的防护机制上一次真实触发是什么时候?
- [ ] 你的远端管理界面在低配机上花掉了多少资源?
